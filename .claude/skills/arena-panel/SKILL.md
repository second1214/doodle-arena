# arena-panel — サブエージェント検討会

1人で考えると「今のやり方の延長」と「全部やる/全部やめる」の二択に寄りやすい。観点の違う担当を並べて、
具体的な案と数字を持ち寄らせ、私（オーケストレータ）が突き合わせてユーザーに提案する。

> 出自: この会話で3回行った手作業（仕様レビュー3名 / プレイテスト2名 / 設計2名）を手順化したもの。
> 骨格は Nexus の nexus-review（役割分担・擁護役・別案必須）と nexus-research（往復に上限・人に返す）から引き継いだ。

## 原則

1. **観点を分ける**: 担当ごとに見る範囲を明示し、他の担当の領域には踏み込ませない（重複は無駄、漏れは担当表で防ぐ）。
2. **ユーザーの指示を薄めない**: 担当の誰か（または私の統合時）が、ユーザーの言葉を最強の形で実現する側に立つ。
   「手間がかかる」「優先度が低い」を理由に指示を縮めた案は差し戻す。縮める理由が本当に必要（技術的に不可能・ブラウザの制約・無料枠を超える等）なら、その理由を明記してユーザーに確認する。
3. **別のやり方を最低1つ**: 各担当は今の作りの延長ではない根本的に違う案を1つ以上出す。
4. **数字で語る**: バランス・難易度・性能の話は、可能な限りシミュレーションや実測の数字を付ける（感想だけの指摘は弱い）。
5. **提案で止める**: 担当の結論を採否にしない。私が突き合わせて提案し、**ユーザーの合意を得てから実装**する。
6. **上限**: 1回の検討会は担当最大4名・往復最大2回。まとまらなければ、まとまった所と未解決の所を分けてユーザーに返す。

## 型と担当の組み合わせ（既定。依頼に合わせて入れ替えてよい）

| 型 | 使う場面 | 担当（既定） |
|:--|:--|:--|
| review | 仕様・設計案の穴探し | ①技術（実現性・スマホ性能・データ構造）②ゲームデザイン（面白さ・壊れ方・続ける理由）③運営（不適切投稿・不正・費用・法律、無料運用） |
| playtest | ビルドを実際に遊ばせる | ①手触り（見た目・操作・演出・音、スクショを撮って見る）②バランス（戦法ボットを総当たりさせ勝率表、抜け道探し） |
| design | 新機能の具体案 | 依頼を構成要素に分け、要素ごとに1名（例: 形→性能の対応 / 近接必殺の効果一覧）。必要なら③ユーザー意図擁護（指示の核が削られていないか監査）を追加 |

## 手順

1. **依頼を分解**して型と担当を決め、担当表をユーザーに一言で伝える（例:「技術・デザイン・運営の3人に並行でレビューさせます」）。
2. **材料をそろえる**:
   - review/design: 検討対象を `docs/` か作業用メモ（scratchpad）に書き出し、絶対パスで渡す。
   - playtest: 現在のコミットの**読み取り専用スナップショット**を作る（担当が作業中のコードと衝突しないように）:
     ```sh
     git -C <repo> worktree add <scratch>/playtest HEAD --detach
     ln -s <repo>/node_modules <scratch>/playtest/node_modules
     (cd <scratch>/playtest && npx vite build --mode single)   # dist/index.html を遊ばせる
     ```
     終わったら `git -C <repo> worktree remove --force <scratch>/playtest`。
3. **担当を並行で起動**（Agent ツール・`run_in_background: true`・1メッセージで全員）。プロンプトに必ず含める:
   - 役割と**見ない範囲**（他担当の領域）
   - リポジトリは**読み取り専用**、書いてよいのは各自の作業ディレクトリ（`<scratch>/<担当名>`）だけ
   - ユーザーの決定済み事項（docs/SPEC.md の §0 など）は**蒸し返さない**こと
   - 「現行と根本的に違う案を最低1つ」
   - 報告は**日本語・平易**（専門用語は説明付き）、文字数上限、見出しの型（例: 重大な指摘 / 改善案 / 数字 / 仕様に追記すべき決定事項）
   - ツール使用回数の目安（例: 40回以内）
   - 環境メモ（下記）
4. **待つ**: 完了通知が来るまで結果を推測しない。ユーザーには「実行中」とだけ伝える。
5. **突き合わせ**（私がやる）:
   - 担当間の矛盾を解く（どちらを採るか、理由付き）
   - **今の版で既に直っている指摘**を分ける（担当は古いスナップショットを見ていることがある）
   - ユーザーの指示から縮められた案がないか確認（原則2）
6. **ユーザーへ提案**: 次の形で締める。
   - 対応済みの表 / 新しく分かった問題の表（数字付き）/ 改善案の表（記号・中身・効果の見込み）
   - 判断してほしいこと（番号付き、おすすめを明記）
   - 実装はしない。合意の言葉を受け取ってから実装に入る。
7. 合意後に実装したら、決定を `docs/SPEC.md` に反映する。

## 環境メモ（担当に渡す）

- Playwright: `require('/opt/node22/lib/node_modules/playwright')`。起動引数 `['--use-gl=swiftshader','--enable-webgl','--ignore-gpu-blocklist']`、スマホ想定は viewport 390×844・`hasTouch: true`。`playwright install` はしない。
- 画面操作: タブ `button[data-view=draw|detect|anim|battle]`、サンプル絵 `#sample`、相手 `#cpuChar`、必殺効果はラベル文字をクリック、観戦 `#spectate`、開始 `#startBattle`。戦闘中のキー: WASD 移動 / J 攻撃 / K 防御（押しっぱなし）/ L 必殺。
- 戦闘計算は `src/sim/world.ts`（DOM 非依存・決定的）。ボット対戦は vitest で回す。**vitest は console 出力を隠すので結果は node:fs でファイルに書く**。数値を変えて試すときは world.ts を作業ディレクトリに**コピー**して変える（本体は編集しない）。
- ヘッドレスの WebGL は遅い。見た目は判断してよいが、フレームレートは判断しない。
- スクショは Read ツールで実際に見て判断する。並べて見たいときは Playwright で画像を1枚のページに並べて撮る。
